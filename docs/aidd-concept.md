# AIDD(AI 駆動開発)の構想

このドキュメントは、本リポジトリで実践している AIDD(AI-Driven Development:AI 駆動開発)の考え方と進め方をまとめたものです。同じ進め方をほかのプロジェクトやメンバーに広げるとき、また進め方を振り返って改善するときの基準として使います。

- 対象読者: このリポジトリの開発に参加する人、同じ進め方を別のプロジェクトで試したい人
- 前提: AI エージェントには Claude Code を使う。コードやドキュメントの変更は GitHub の Issue と PR で管理する

## 1. 目的と、この PoC で確かめたいこと

### 目的

人は「何を作るか」と「それでよいか」の判断に集中し、実装・テスト・PR 作成・レビューといった作業の大部分を AI に任せる。そのうえで、品質を人が手で担保するのと同じ水準に保つ。

### この PoC で確かめたいこと

小さなカンバン型タスク管理アプリ(仕様は [要件定義書](requirements.md))を題材に、次の点を確かめる。

1. 要件定義から実装・レビュー・マージまでを、Issue 単位で AI に任せて進められるか
2. ルールや手順をファイル(`CLAUDE.md`・ルールファイル・設定ファイル・サブエージェント・スキル)として渡すことで、AI の出力のぶれを抑えられるか
3. テスト・画面確認・レビューの繰り返しで、人が手で確認するのと同等の品質を保てるか
4. AI だけでは判断・確認できないことは何か。人が関わるべき場面はどこか

## 2. 開発フロー

1つの機能を、次の流れで Issue からマージまで進める。

```
要件定義 ──→ 実行計画 ──→ Issue の起票(/create-issue)
                              │
                              ▼
               /implement-issue <Issue番号>
     (ブランチ作成 → 実装 → コミット → 動作確認 → PR 作成)
                              │
                              ▼
                  /pr-review <PR番号>(PR にコメント)
                              │
                   指摘あり ──┴── 指摘なし
                      │               │
                      ▼               ▼
              指摘の修正・プッシュ   人がマージ
                      │
                      └──→ /pr-review で再レビュー
```

| 工程 | 内容 | 主な担い手 | 成果物 |
| --- | --- | --- | --- |
| 要件定義 | アプリの仕様・異常系・非機能要件を決める。新規作成は Plan モード、追加は `/implement-plan` で進める | 人が決める。文書化は AI と進める | [docs/requirements.md](requirements.md)(#3) |
| 実行計画 | 要件を実装 Issue に分け、依存関係・着手順序・担当のサブエージェント・完了条件を決める。新規作成は Plan モード、追加は `/implement-plan` で進める | 人と AI で作り、人が確認する | [docs/execution-plan.md](execution-plan.md)(#5) |
| Issue の起票 | 計画にもとづき、`/create-issue` で概要・背景・対応内容(案)・完了条件を書いた Issue を作る | 人と AI で作り、人が確認する | GitHub の Issue(#6〜#12、#21) |
| 実装 | `/implement-issue` で、ブランチの作成から PR の作成までを行う | AI | ブランチ・コミット・PR |
| レビュー | `/pr-review` で差分をレビューし、結果を PR にコメントする | AI | PR のコメント |
| 修正と再レビュー | 指摘を修正してプッシュし、指摘がなくなるまで再レビューする | 修正するかどうかは人が決め、修正は AI が行う | 追加のコミット・PR のコメント |
| マージ | 最終的な判断をしてマージする | 人 | main ブランチ |

要件定義と実行計画は後のすべての作業の前提になるため、AI が調べた内容と人の判断をすり合わせ、人が了承してから文書にする。進め方は、追記先のドキュメントがあるかどうかで使い分ける。

- 要件定義書・実行計画をゼロから作るとき: Claude Code の Plan モードで進める。Plan モードの AI は、コードやドキュメントを読んで調べ、案を示すだけで、ファイルを変更する操作はしない。人が案を確認・修正して承認してから、ドキュメントの作成に移る。
- 作成済みの要件定義書・実行計画に機能を追加するとき: `/implement-plan <計画したい内容>` を使う。影響範囲の調査と決めるべき点の質問をしたうえで、追記する内容を一覧にして示し、人の了承を得てから両方に追記してブランチにプッシュする。Plan モードの中ではファイルを変更できないため、`/implement-plan` は Plan モードの外で実行する。

## 3. 人と AI の役割分担

| 人が決めること | AI に任せること |
| --- | --- |
| 何を作るか(要件・優先度・スコープ) | 要件定義書・実行計画・Issue の文章化 |
| レビューの指摘を直すかどうか | 実装・ユニットテストの作成 |
| マージするかどうか | コミット(目的ごとの分割と絵文字の付与を含む)・プッシュ・PR 作成 |
| 開発環境の変更(ソフトウェアの導入、MCP の設定など) | 型チェック・Lint・ビルド・テストの実行と、失敗したときの修正 |
| AI に与える権限の範囲 | headless ブラウザでの画面確認 |
| AI の説明があいまいなとき、または仕様の解釈が分かれるときの判断 | PR のレビューと、PR へのコメント |
| 実機・支援技術(スクリーンリーダーなど)での確認 | 指摘への対応 |

AI は、判断が必要な場面では作業を止めて人に確認する。これまでに人に判断を求めた例は次のとおり。

- 画面確認用のブラウザをどの方法で導入するか(#10)
- ユーザーの報告が不具合か期待どおりの動作か、はっきりしない場合(#11 の「Enter で送信されていた」)
- 自動モードの安全判定で止まった操作(`CLAUDE.md` へのコミット)をどうするか

## 4. AI に渡すルールと仕組み

AI の出力のぶれを抑えるため、ルールや手順は会話で毎回伝えるのではなく、リポジトリのファイルとして渡す。

### 4.1 CLAUDE.md

Claude Code がセッションの開始時に必ず読み込むプロジェクトの指示です。次の内容を書いている。

- アプリケーションの概要とスコープ外の機能
- 技術スタックと、コンポーネントを責務ごとに分割する方針
- ブランチの命名規則(`feature/#Issue番号` など)と、main へ直接コミットしないこと
- コミットの規則(目的ごとに分割し、内容に応じた絵文字を付ける)

### 4.2 ルールファイル(`.claude/rules/`)

コーディングルールを、領域ごとのファイルに分けて書いている。メインのセッションで直接作業するときも、サブエージェントに任せるときも、`/pr-review` でレビューするときも、同じルールを参照する。

| ファイル | 読み込むタイミング | 内容 |
| --- | --- | --- |
| `general.md` | 常に(セッションの開始時) | スコープを広げないこと・条件の書き方・コメントの方針・`next dev` を起動しないこと |
| `typescript.md` | `*.ts`・`*.tsx`・`*.mts` を扱うとき | `any` を避ける(具体的な型・ジェネリクス・`unknown` を優先)・`import type`・型の置き場所(タスクと列の型は `src/types/task.ts`) |
| `components.md` | `src/components/`・`src/app/`・`src/hooks/` のファイルを扱うとき | コンポーネントの分け方・タスクのデータの扱い・Tailwind CSS の書き方・アクセシビリティ |
| `task-logic.md` | `src/lib/` のファイルを扱うとき | 純粋関数の作り方・ステータスの扱い・バリデーション・localStorage への保存と読み込み |
| `testing.md` | `src/**/*.test.ts`・`src/**/*.test.tsx` を扱うとき | テストの置き場所と対象・React Testing Library でのコンポーネントのテスト・書き方・してはいけないこと |

- `general.md` 以外は、先頭の `paths` で対象のファイルを指定している。Claude Code は、対象のファイルを読み書きしたときにだけそのルールを読み込むため、関係のない作業ではコンテキストを使わない。
- `CLAUDE.md` には、アプリの概要・技術スタック・Git の規則だけを書き、コーディングルールはルールファイルに書く。
- ルールは、すでにあるコードの書き方から作っている。コードの書き方を変えたときは、ルールファイルも合わせて直す。

### 4.3 サブエージェント(`.claude/agents/`)

作業の領域ごとに、専門のサブエージェントを用意している。実行計画で Issue ごとに担当を決め、`/implement-issue` の中で担当のサブエージェントに実装を任せる。サブエージェントの定義には担当範囲と完了時の確認だけを書き、実装の方針はルールファイルを読ませる。

| サブエージェント | 担当 | 使えるツール |
| --- | --- | --- |
| `frontend-developer` | UI コンポーネント・スタイリング・フォーム・ドラッグ&ドロップ | ファイルの読み書き・Bash |
| `backend-developer` | データモデル・永続化(localStorage)・ステータス更新などのロジック | ファイルの読み書き・Bash |

実装をサブエージェントに任せるときは、呼び出す側(メインのセッション)が次の内容を依頼文に書く。

- 参照すべき要件定義書の章と、既存のコード
- Issue の対応内容と完了条件
- してはいけないこと(コミットしない、`next dev` を起動しない、スコープ外の機能を足さない、など)
- 報告してほしい内容(変更したファイル、設計判断、画面確認で見るべき点)

サブエージェントが作業を終えたら、メインのセッションが差分を確認してからコミットする。サブエージェントの報告だけをもとにコミットはしない。

レビューはサブエージェントには任せず、`/pr-review` をメインのセッションで実行する。以前はレビュー専用の `code-reviewer` を用意していたが、実際のフローでは使われていなかったため廃止し、その観点を `/pr-review` に取り込んだ。

### 4.4 スキル(`.claude/skills/`)

繰り返し行う作業の手順を、スキルとして固定している。スキルは `.claude/skills/<スキル名>/SKILL.md` に置き、`/スキル名` で呼び出す。

以前はカスタムコマンド(`.claude/commands/`)に置いていたが、スキルに移した(#31)。カスタムコマンドとの違いは次の2点で、カスタムコマンドを残す理由がないため廃止した。

- `description` に合う依頼をしたときに、AI が判断して自動で読み込む。`/スキル名` と打たなくても、「Issue を起票して」のような依頼で同じ手順が使われる。そのため `description` には、何をするかに加えて、どんな依頼のときに使うかを書く。
- 手順と一緒に補助ファイル(テンプレートなど)を同じディレクトリに置ける。補助ファイルは AI が必要なときだけ読むため、手順の本文を短く保てる。

自動で読み込ませるかどうかは、すべてのスキルで許可している(`disable-model-invocation` は指定しない)。ブランチの作成・プッシュ・Issue や PR の作成のように外に影響する操作は、スキルの手順の中で了承を得るか、`.claude/settings.json`(4.5)の設定で制限する。自動で呼ばれたときは引数が渡らないことがあるため、引数が必要なスキルは、空の場合にチャットで質問する手順を入れている。

| スキル | 手順 |
| --- | --- |
| `/create-issue <起票したい内容>` | 起票内容を受け取る(ない場合はチャットで質問する) → 関係するドキュメントとコード、既存の Issue を調べる → 内容があいまいなら質問する → テンプレート(`template.md`)に沿って本文を書き、チャットで示して了承を得る → `gh issue create` で起票する |
| `/implement-plan <計画したい内容>` | 計画内容を受け取る(ない場合はチャットで質問する) → 既存のドキュメントとコードから影響範囲を調べる → 決めるべき点を質問する → 追記内容を一覧で示して了承を得る → 要件定義書と実行計画に追記する → 別々にコミットしてブランチにプッシュする(コードは変更せず、PR も作らない) |
| `/implement-issue <Issue番号>` | Issue 番号を受け取る(ない場合はチャットで質問する) → Issue と関連ドキュメントを確認する → 新しいブランチを切る → 担当のサブエージェントで実装する → 目的ごとにコミットする → ビルド・型チェック・Lint・テストと画面確認で確認する → PR を作成する |
| `/pr-review [PR番号 \| ブランチ名]` | 差分を取得する → 変更されたファイルに対応するルールファイルを読む → ルールファイルと一般的な正しさの観点でレビューする → 決まった形式で PR にコメントする |

`/create-issue` のテンプレートでは、完了条件を確認の方法ごとに「コマンドで確認する項目」「AI が headless ブラウザで確認する項目」「人が確認する項目」に分けて書く(6.5)。

`/pr-review` のレビューの観点は次のとおり。

- ルールファイル: 常に `general.md` を読み、変更されたファイルに応じて `typescript.md`・`components.md`・`task-logic.md`・`testing.md` を読んで、差分がルールに沿っているかを確かめる
- 一般的な正しさ: バグ・エッジケース・エラーハンドリングの過不足

指摘には重要度(高・中・低)と、ファイルパス・行番号を付け、可能であれば修正案を添える。ルールファイルに基づく指摘には、根拠にしたルールファイル名を添える。根拠のない指摘はしない。レビューだけに専念し、コードは修正しない。

### 4.5 設定ファイル(`.claude/settings.json`)

AI が実行してよい操作・してはいけない操作を、文章のルールではなく設定として強制する。リポジトリで共有するため、誰がどの環境で作業しても同じ制限がかかる。

| 区分 | 対象 | 理由 |
| --- | --- | --- |
| 許可(`allow`) | `npm run build`・`npm run lint`・`npm test`・`npx tsc --noEmit`・`npx vitest`・`npx next start`、`git` の参照・ブランチ操作・`add`・`commit`・`push`、`gh` の Issue・PR の参照・作成・編集・コメント | 毎回行う操作で、確認を出さずに進めるため |
| 確認(`ask`) | `git reset --hard`(オプションを後ろに書いた場合も含む)、ブランチの削除(`git push --delete`・`-d`、`git branch -D`)、コミットしていない変更の破棄(`git checkout -- <パス>`・`git checkout .`) | 履歴の書き換えや削除は元に戻しにくいため。必要な場面があるので禁止はせず、毎回人が確認する |
| 拒否(`deny`) | `npm run dev`・`next dev`・`npx next dev`、`.env`・`.env.*` の読み取り | `CLAUDE.md` への自動追記を防ぐため(6.2)。秘密情報を読ませないため |
| フック(`PreToolUse`) | `git commit` の前に、`CLAUDE.md` に `nextjs-agent-rules` のブロックがあればコミットを止める | 拒否をすり抜けて追記された場合でも、コミットに混ぜないため |
| フック(`PreToolUse`) | `git push` に `:<ブランチ>`(リモートのブランチの削除)が含まれていれば確認を求める | コロンを含む形は、許可・確認の規則では照合できなかったため |
| フック(`PreToolUse`) | `rm` の再帰かつ強制の削除(`-rf`・`-fr`・`-r -f`・`--recursive --force` など)、force push(`--force`・`--force-with-lease`・`-f`・`+<refspec>`。オプションの位置は問わない)、`sudo` を止める。`/bin/rm` のようなパスつき、サブシェル・コマンド置換の中、`git -C <ディレクトリ> push` のようにグローバルオプションを挟んだ形も対象にする(`.claude/hooks/block-dangerous-command.sh`) | 取り返しのつかない削除・履歴の上書き・権限昇格を AI に実行させないため。force push は人が実行する |
| フック(`PostToolUse`) | `Edit`・`Write` で `.ts`・`.tsx`・`.mts` を編集した後に、そのファイルの ESLint と、そのファイルに関係するテスト(`vitest related`)を実行し、失敗したら結果を Claude に返す(`.claude/hooks/check-after-edit.sh`) | Lint とテストの失敗に編集の直後に気づき、その場で直させるため。編集のたびの待ち時間を抑えるため、対象を編集したファイルに関係する範囲に絞る |
| フック(`Stop`) | 応答が終わったら、Windows のデスクトップにトースト通知を出す(`.claude/hooks/notify-done.sh`。WSL 以外では何もしない) | 長い作業の完了に、画面を見ていなくても気づけるようにするため |

- 許可・確認・拒否が重なる場合は、拒否 → 確認 → 許可の順に優先される。`git push` 全体を許可したうえで、force push はフックで止めている(フックは許可・確認の判定より先に働く)。
- 規則はコマンドの文字列で照合する。`git reset HEAD~1 --hard` のようにオプションを後ろに書く形も、途中にワイルドカードを置いた規則(`git reset * --hard*`)で確認の対象にしている。
- `git checkout -- CLAUDE.md`(コミット前のフックが案内する戻し方)も確認の対象になる。
- 信頼済みにしていないワークスペースでは、プロジェクト設定の `allow` が読み込まれない(headless の `claude -p` で確認した)。新しい環境では、一度 Claude Code を対話モードで起動し、信頼の確認に同意する。
- 個人の設定は `.claude/settings.local.json` に書く。`.gitignore` には入れていないため、コミットしないよう注意する。

### 4.6 ドキュメントを AI の作業の入力にする

要件定義書と実行計画は、人が読むためだけでなく、AI の作業の入力としても使う。

- Issue の本文に、要件定義書の参照すべき章(例: 「4.3 全体・2.2・3.3」)を書く。AI は実装の前にその章を読む。
- 実行計画に、Issue ごとの担当のサブエージェント・依存関係・完了条件・主なファイルを書く。AI はそれに従ってブランチの起点や作業範囲を決める。
- 仕様の判断に迷ったときは、会話での指示ではなく、ドキュメントの記述を根拠にする。

## 5. 品質を担保する仕組み

| 段階 | 内容 |
| --- | --- |
| ユニットテスト・コンポーネントのテスト | UI から切り離したロジック(入力の検証・タスクの作成と移動・保存と読み込み・Enter キーでの送信判定・隣の列の選択など)を Vitest でテストする。観点は要件定義書 6章で決めておく。コンポーネントは React Testing Library で、ユーザーから見える操作に対する振る舞いをテストする |
| 自動チェック | コミットの後に `npm run build`・`npx tsc --noEmit`・`npm run lint`・`npm test` の順に実行し、すべて成功することを確かめる。型は Next.js がビルド時に生成するため、型チェックはビルドの後に行う |
| 画面確認 | 本番ビルドを `next start` で起動し、headless Chrome を Playwright で操作して、Issue の完了条件の画面確認の項目を1つずつ確かめる。タッチ操作は Chrome DevTools Protocol でタッチイベントを送って再現する |
| テストの有効性の確認 | テストを追加したときは、実装を一時的に壊すとそのテストが失敗することを確かめてから元に戻す(ミューテーションの確認) |
| レビュー | `/pr-review` でレビューし、指摘がなくなるまで修正と再レビューを繰り返す |

この仕組みで、実際に次のような問題を見つけている。

- 画面確認で見つかった不具合: 背景で押してダイアログの上で離すと、モーダルが閉じてしまう(#11)
- レビューで見つかった不具合: 文字数カウンターの赤字と、送信時のエラーが食い違う。送信エラーがスクリーンリーダーで読み上げられない(#11)
- レビューで見つかった不具合: ドラッグできるカードのアクセシブルネームが空になる(#12)。指摘の前に、レビュー側がアクセシビリティツリーで事実を確かめてから指摘した
- レビューで見つかったテストの不足: ストアの保存・通知の挙動にテストがない(#10)、テストの部分一致で件数の誤りを見逃す(#9)

## 6. 運用で分かった注意点と課題

### 6.1 画面確認の環境づくり

- headless ブラウザでの画面確認には、ブラウザ本体が必要になる。この環境では最初は用意されておらず、人の判断で Google Chrome を導入した。
- root で動かす Chrome はサンドボックスを外す必要がある。Playwright MCP では起動オプションに `--no-sandbox` を付ける必要があり、MCP の設定を変えた後は Claude Code の再起動が必要になる。
- MCP を使えない間は、作業用のディレクトリに `playwright-core` だけを入れ、スクリプトから Chrome を直接操作して確認した。プロジェクトの依存関係は増やしていない。

### 6.2 `next dev` による `CLAUDE.md` への自動追記

- Next.js 16 は、AI エージェントの環境で `next dev` を起動すると、`CLAUDE.md` の末尾に `<!-- BEGIN:nextjs-agent-rules -->` のブロックを自動で追記する。
- 意図しない差分が生まれるため、AI が画面確認をするときは `next dev` ではなく、`npm run build` の後に `next start` で起動する。
- 追記を止めたい場合は、`next.config` で `agentRules: false` を指定する。
- `.claude/settings.json` で `next dev` の起動を拒否し、`git commit` の前に追記のブロックがないかをフックで確かめている(4.5)。

### 6.3 自動モードの安全判定

- Claude Code の自動モードでは、AI が実行しようとした操作が安全判定で止められることがある。例として、ツールが生成した AI 向けの指示文を `CLAUDE.md` にコミットする操作は、人の指示があっても止められた。
- 止められた操作を、別の方法で言い換えて実行し直すことはしない。理由を人に説明し、人が自分で実行するか、権限の設定を見直すかを決める。
- 履歴を書き換える操作のうち、force push はフックで止めて人が実行し、`git reset --hard` は `.claude/settings.json` で毎回確認する設定にしている(4.5)。ただし自動モードの安全判定は設定とは別に働くため、確認の設定があっても判定で止められることがある。

### 6.4 確認用スクリプトの誤り

- 画面確認のスクリプトが、実装ではなくスクリプト自身の誤りで NG になることがある(例: 背景で押して離す操作が、正しい「背景クリックで閉じる」動作になっていた)。
- NG が出たときは、すぐに実装を直さず、スクリプトの操作が意図どおりかを先に確かめる。

### 6.5 AI だけでは確認しきれないこと

次の項目は headless 環境では確認できないため、人が実機で確かめる必要がある。

- 実際の IME(日本語入力)で変換を確定する Enter の挙動。特に Safari
- 実機でのタッチ操作(長押し・スワイプ)
- スクリーンリーダーでの実際の読み上げ(AI はアクセシビリティツリー上の名前や属性までを確かめる)

### 6.6 今後の課題

- 画面確認のスクリプトを、作業用のディレクトリではなくリポジトリに置き、E2E テストとして繰り返し実行できるようにするか検討する。
- ユーザーの報告があいまいなときの確認の仕方(何を、どの環境で試したか)を、テンプレートとして決めておく。
