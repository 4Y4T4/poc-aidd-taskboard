# Issue の書式

## タイトル

- 「〜を実装する」「〜を追加する」「〜を作成する」のように、完了したときの状態が分かる動詞で終える。
- 例: `保留ステータスの列を追加する`、`Claudeのルールファイルを作成する`

## 本文

次の見出しの順に書く。当てはまる内容がない見出し(「決めること」など)は省略する。

```markdown
## 概要
何をするのかを1〜2文で書く。

## 背景
なぜ必要なのか(今の状態と、それで困っていること)を書く。

- 担当: <サブエージェント名>(理由があれば括弧で添える)
- 依存: #<Issue番号>(先にマージが必要な Issue があれば書く)
- change: `openspec/changes/<change名>/`(仕様を変える場合)
- 参照: `openspec/specs/<capability>`、関係するファイル・ドキュメント

## 決めること(着手前に確認する)
- [ ] <決めること>: 案は「<推奨する案>」(<理由>)
    - 選択肢が複数ある場合は、案ごとに長所・短所を書く

## 対応内容(案)
- change がある場合: `openspec/changes/<change名>/tasks.md` のとおり(作業のまとまりだけを要約して書く)
- [ ] <作業のまとまり>
    - <具体的な作業と、対象のファイル>
- [ ] ドキュメント
    - 更新が必要なドキュメントと章

## 完了条件
- `npm run build` / `npx tsc --noEmit` / `npm run lint` / `npm test` が成功すること
- 以下のユニットテストがあり、成功すること
    - <テストの観点>
- 以下を画面で確認していること(headless ブラウザで AI が確認する)
    - <確認する操作と、期待する表示>
- 以下を人が確認していること(headless ブラウザでは確認できない項目)
    - <実機のタッチ操作・実際の IME・スクリーンリーダーの読み上げなど>
```

## 書き方の注意

- 「担当」は、`.claude/agents/` の各サブエージェントの担当範囲(データ層は backend-developer、UI は frontend-developer)に合わせる。change がある場合は、`tasks.md` に書かれた担当と合わせる。ドキュメントや `.claude/` の設定など、どちらにも当たらない作業は書かない。
- change がある場合、仕様の詳細(要件・シナリオ)は Issue に写さず、change を参照する。完了条件の確認項目は、仕様の差分のシナリオから選ぶ。
- 完了条件は、確認の方法(コマンド・画面・人)が分かるように書く。コードやドキュメントだけの変更で、テストや画面確認がない場合は、該当する項目を省略し、確認方法(例: `/memory` で読み込まれることを確認する)を書く。
- 「人が確認する項目」は、AI が headless ブラウザで確認できない項目だけを書く。AI が確認できる項目と混ぜない。
- 対応内容は「案」として書き、着手時に変わってもよいものにする。完了条件は、着手前に決めることの結果によらず満たすべき状態を書く。
